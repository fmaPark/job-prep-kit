# 폴더 구조와 설계 배경

## 왜 이 구조인가

취업 준비 파일이 망가지는 방식은 대개 정해져 있습니다. 회사별 폴더에 자소서를 쓰다 보면
같은 경험이 폴더마다 조금씩 다른 문장으로 복제되고, 3~4곳쯤에서 "내 최신 이력이 어느 폴더에 있더라"가 시작됩니다.

이 저장소의 전제는 하나입니다.

> **축적은 `me/`에, 소비는 `applications/`에.**

`me/`만이 사실의 출처입니다. 회사 폴더는 사실을 저장하지 않고 조합만 합니다.
그리고 회사 폴더에서 얻은 새 자기이해는 반드시 `me/`로 되돌립니다. 이 되돌림이 없으면
지원 건이 늘어날수록 매번 처음부터 시작하게 됩니다.

세 가지 설계 결정이 여기서 나옵니다.

**경험은 자소서 문항이 아니라 사건 단위로 쪼갭니다.**
"성장 경험" 같은 문항 단위로 저장하면 회사가 바뀔 때마다 다시 씁니다.
사건 단위로 쪼개면 같은 경험을 다른 직무나 트랙(예: 개발과 PM, 마케팅과 영업)에서 다르게 잘라 쓸 수 있습니다.

**자소서보다 전략 매핑이 먼저입니다.**
회사 폴더의 `strategy.md`에 공고 요구사항 ↔ 내 경험 매핑표를 채웁니다.
**비어 있는 칸이 곧 면접 압박 질문**입니다. 이걸 건너뛰고 자소서부터 쓰면 매번 백지에서 시작합니다.

**결과는 `library/`에 누적됩니다.**
면접에서 실제로 받은 질문, 필기·과제에서 틀린 유형, 지원 회고. 지원 건수가 늘수록
여기가 두꺼워져야 합니다. 회고만 쌓이고 필기·과제 복기가 비어 있다면, 자소서를 아무리 다듬어도
같은 자리에서 막힙니다.

## 폴더 구조

```
.
├── index.md                  # 번들 목차 (OKF 예약 파일)
├── log.md                    # 변경 이력
├── CLAUDE.md                 # AI 작업 규칙 — 시스템 인스트럭션
├── playbook.md               # 단계별 워크플로우
├── build-dashboard.py        # 대시보드 생성기
├── docs/                     # 이 안내 문서들
│
├── me/                       # ① 사실의 단일 출처
│   ├── profile.md            # 기본 정보
│   ├── narrative.md          # 모든 자소서가 공유하는 한 줄 서사
│   ├── skills.md             # 역량 ↔ 증명 경험
│   ├── target-criteria.md    # 지원 여부 판단 기준
│   ├── portfolio.md          # 프로젝트별 문제·결정·결과
│   ├── experiences/          # 사건 단위 경험 원자 (+ _template.md)
│   └── assets/               # 이력서·포폴 원본 (.gitignore 처리됨)
│
├── applications/             # ② 지원 현황 — 폴더 하나 = 지원 건 하나
│   ├── index.md              # 파이프라인 보드
│   └── _template/            # 회사 폴더 템플릿 (통째로 복사해서 사용)
│       ├── meta.md           #   상태 메타데이터 — 대시보드가 읽는 파일
│       ├── jd.md             #   공고 원문 (요약 금지)
│       ├── research.md       #   회사·제품·조직 조사
│       ├── strategy.md       #   공고 ↔ 경험 매핑표  ← 여기가 핵심
│       ├── cover-letter.md   #   자기소개서 (+ drafts/ 버전 이력)
│       ├── interview.md      #   예상 질문·꼬리질문
│       ├── assessment.md     #   필기·과제(코테·인적성·과제) 대비
│       └── log.md
│
└── library/                  # ③ 회사를 가로지르는 자산
    ├── question-bank.md      # 실제로 받은 면접 질문
    ├── assessments/          # 필기·과제 틀린 유형 누적
    └── retrospectives/       # 지원 회고 → me/로 반영
```

## 이름 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| 경험 원자 파일 | `YYYY-키워드.md` | `2024-결제모듈-장애대응.md` |
| 회사 폴더 | `YYYY-MM-회사명-직무` | `2026-09-토스-백엔드`, `2026-10-오늘의집-마케팅` |
| 이력서 등 원본 | `YYYY-MM-이력서-버전.pdf` | `2026-09-이력서-v3.pdf` |
| 샘플 데이터 | 이름이 `_sample`로 시작 | 대시보드에 "샘플" 표시가 붙습니다 |

`_template`으로 시작하는 파일과 폴더는 대시보드가 세지 않습니다.

## 직군과 전형 종류

템플릿은 특정 직군을 가정하지 않습니다. `meta.md`의 `track`은 자유 텍스트(개발, PM, 디자인, 마케팅, 데이터, 영업, 사무 …)이고, 필기·과제 전형은 코딩테스트 · 인적성 · 과제 · PT · 어학을 모두 같은 자리에서 다룹니다.
지원 단계는 대시보드가 필터로 쓰기 때문에 6개 큰 범주로 고정되어 있고, 2차 면접이나 인턴 전환처럼 세부 단계는 `stage_note`에 적습니다.

## 문서 규격 (OKF 0.2)

문서는 [OKF 0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md) 규격을 따릅니다.
규격을 몰라도 쓰는 데 지장은 없습니다. 실제로 지켜야 할 것은 아래뿐입니다.

- `index.md`와 `log.md`를 제외한 모든 마크다운 문서는 맨 위에 `---`로 감싼 프론트매터를 두고, 거기에 `type`을 적습니다 (`Experience`, `Strategy`, `Cover Letter`, `Application` …). 템플릿에 이미 들어 있으니 복사해서 쓰면 됩니다.
- 대시보드가 실제로 읽는 필드는 셋입니다.
  - `stale_after` — 회사 리서치처럼 시의성 있는 문서의 재조사 신호
  - `status: draft` — 아직 못 채운 문서. 대시보드가 세어서 보여줍니다
  - `sources` — 자소서에 쓴 수치의 출처

## 링크 규칙

문서끼리는 두 가지 방식으로 연결되어 있습니다. **둘 다 Obsidian에서 열어 보는 것을 기준으로 합니다.**

| 방식 | 예 | 어디서 동작하나 |
|---|---|---|
| 루트 기준 절대경로 | `[역량](/me/skills.md)` | Obsidian, GitHub 웹. VS Code 미리보기에서는 열리지 않습니다 |
| 위키링크 | `[[/me/experiences/2024-키워드]]` | Obsidian 전용. 다른 편집기에서는 그냥 글자로 보입니다 |

템플릿의 `[[확인필요: …]]` 표시는 링크가 아니라 **"근거를 아직 못 댔다"는 할 일 표시**입니다.
Obsidian에서는 존재하지 않는 문서로의 링크처럼 보이는데, 그게 의도입니다. 다 지워지면 그 문서는 제출해도 되는 상태입니다.

대시보드는 회사 폴더 안 문서에 경험 파일 이름이 등장하면 "참조 1회"로 셉니다.
링크 방식과 무관하게 파일 이름(확장자 제외)만 들어 있으면 됩니다.
