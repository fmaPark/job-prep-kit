# 포트폴리오 작성 규칙

> 시각 디자인 · 레이아웃 제작은 빼고, 입력 · 규칙 · 출력으로 정할 수 있는 것만 담았다.
> "프로젝트"는 개발 프로젝트만이 아니다. 캠페인, 행사, 연구, 디자인 작업처럼 문제와 결과가 있는 일의 단위면 된다.

## A. 범위

- **목적**: 소재(경험 원자)가 `/me/`에 정해진 상태에서 케이스 스터디형 포트폴리오 본문과 README 초안을 만든다.
- **산출물**: ① PDF · 슬라이드용 본문 ② 공개 저장소 README ③ 프로젝트 1장 요약 카드.
- **비적용**: 시각 디자인, 실제 작업물 제작, 없는 성과 창작.
- 무엇을 공개 증빙으로 쓸 수 있는지는 [/me/portfolio.md](/me/portfolio.md) 「공개 범위」를 따른다.

## B. 시작 전 입력

정본에 없는 칸은 비워 두고 `[[확인필요: ...]]`로 묻는다.

- 지원 직무와 공고 원문 (필수 요건 · 우대사항)
- 제출 형식과 제약: PDF / 웹 / 노션, 페이지 수, 용량(10MB 제한이 흔하다), 파일명 규칙
- 프로젝트 목록과 대응 경험 원자
  - 이름, 기간, 인원, 본인 역할과 담당 범위
  - 해결하려던 문제와 그 문제를 알게 된 경로
  - 쓴 도구 · 방법 · 기술과 각각을 고른 이유
  - 검토했다 버린 대안과 이유
  - 전후 지표
  - 실패했거나 못 끝낸 부분
  - 결과물 링크 (배포 · 저장소 · 데모 영상 · 문서)
- 개인 정보 공개 범위 (연락처, 링크)
- 비밀유지 · 보안 제약 (있으면 I의 대응 모드)

## C. 구조

### C-1. 분량 · 개수

- **대표 프로젝트 3~5개**를 상세 케이스로. 양보다 질.
- 신입 기준 총 10~20쪽, 최대 30쪽 안쪽. 프로젝트당 상세 3~5쪽 + 요약 1쪽.
- 나머지는 "기타 프로젝트" 한 쪽에 한 줄씩.
- 제출 제약(쪽수 · 용량)이 있으면 제약이 우선한다. 짧은 포트폴리오를 낼 때는 핵심 케이스의 문제 · 역할 · 결과가 빠지지 않게 줄인다.

### C-2. 문서 순서

- 표지: 이름, 직무, 연락처, 링크. 표지 꾸미기에 시간을 쓰지 않는다.
- 한 줄 자기 정의: `/me/narrative.md`의 한 문장에서 가져온다. 성격 · 취미 서술은 넣지 않는다.
- 역량 요약: 숙련도 퍼센트 그래프 대신 "주력으로 쓴 것 / 써 본 것" 두 단. `/me/skills.md` 기준.
- 프로젝트 요약 인덱스 한 쪽: 이름 / 기간 / 역할 / 핵심 결과 한 줄 × 3~5개.
- 프로젝트별 상세 케이스.
- 마지막 쪽: "감사합니다" 대신 연락처와 앞으로 풀고 싶은 문제 한 줄.

### C-3. 케이스 스터디 골격 (7단계)

1. 문제 정의와 가설 — 왜 이 일이 필요했나. 신규 프로젝트라면 세부 문제 나열보다 **만들게 된 배경을 전체 관점에서** 먼저.
2. 본인 역할과 협업 구조 — 팀 구성, 내가 맡은 범위. **팀이 한 일, 내가 한 일, 기여 정도**가 구분되게.
3. 제약 — 기간, 인원, 기술 · 데이터 · 예산 제약.
4. 해결 과정 — 검토한 대안 → 고른 근거 → 실행. 분량을 가장 많이.
5. 결과 — 전후 지표로 검증. 수치가 없으면 비워 두고 정성 결과로.
6. 실패 · 한계 — 채택하지 않은 안, 남은 문제.
7. 배운 점과 다음 개선 계획. 지원 회사에 적용될 수 있는 지점을 소항목으로 둬도 된다.

### C-4. 직무별 추가 섹션

원자에 근거가 있는 것만 넣는다.

- 개발: 구조도 · 데이터 모델 · API 설계, 트러블슈팅 심화(증상 → 원인 추적 → 시도 → 조치 → 재발 방지), 테스트 · 품질, 배포 · 운영, 협업 흔적(리뷰 · 브랜치 전략)
- 디자인: 핵심 의사결정 2~3장면, 검증 방법과 근거, 디자인 시스템 기여
- 마케팅 · 기획: 가설과 실험 설계, 지표 정의, 채널 · 예산 판단
- PM 역할을 했다면 직군과 무관하게 드러낸다.

## D. 문장 규칙

- 도구 · 기술을 나열하지 않는다. 이름 뒤에 "왜 이것을 골랐나"가 한 절 이상 붙어야 한다.
  - 나쁨: "A, B, C로 서비스를 만들었습니다"
  - 좋음: "첫 화면 로딩이 느려 화면 단위로 나눠 불러오게 바꿨고, 측정 기준 3초대에서 1초대로 줄였습니다"
- 결과만 쓰지 않는다. "70% 개선"은 원인 분석 → 조치 → 측정과 함께.
- 성과 문장 형식: **어떤 문제를 / 무엇으로 / 어떻게 해결했고 / 수치는 얼마인가**.
- 수치가 없으면 선택의 장단점 인사이트로 쓴다: "A를 썼더니 ~가 단순해졌다. ~가 필요한 상황이면 B보다 A가 낫다."
- 팀 프로젝트는 본인 담당 범위를 주어로. '우리 팀은'으로 시작하지 않는다.
- 한 문장 한 메시지, 60자 안팎, 피동 · 완곡 어미 없이.
- 개조식 문장의 톤은 가장 최근에 낸 지원서 입력본과 맞춘다(`/me/profile.md` 「지원서 기재 표준」).

## E. 제외 목록

### E-1. 신뢰를 깎는 것

- 튜토리얼 결과물을 차별점 없이 그대로 낸 것
- 접속 안 되는 데모 링크
- 출처 없는 남의 작업물

### E-2. 습관적으로 건너뛰는 페이지 (목적이 없으면 만들지 않는다)

- 숙련도 퍼센트 막대그래프
- 모든 프로젝트에 반복되는 같은 프로세스 도식
- 리서치 근거 없이 상상으로 채운 페르소나
- 와이어프레임 · 시안 전수 나열 (핵심 의사결정 2~3장면만)
- 피드백 전체 나열 (취사선택한 근거만)
- 경쟁사 캡처 나열 (인사이트 한 문단으로)
- 화려한 표지, "Thank you"만 있는 마지막 쪽

### E-3. README

- 너무 긴 README (GitHub는 약 500KiB에서 자른다). 긴 문서는 docs로 나눈다.
- 절대경로 링크 (클론하면 깨진다).

## F. README 구성

공개 가능한 저장소에만 쓴다.

- 한 줄 소개, 왜 만들었고 누가 쓰나
- 데모 GIF · 스크린샷 (위쪽에)
- 배포 · 문서 링크
- 쓴 기술과 고른 이유, 구조도
- 주요 기능, 개선 전후 표
- 실행 방법 (복붙 가능한 명령)
- 알려진 한계, 다음 개선 계획
- 팀 구성과 본인 담당 범위

## G. 출력 형식

- 저장: 구성안은 `applications/<회사>/`에, 초안은 같은 폴더 `drafts/YYYY-MM-DD-portfolio-vN.md`.
- 프로젝트별 케이스 본문 (섹션별 분량 표시), 프로젝트 1장 요약 카드, README 완성본.
- `[수치 필요]` · `[스크린샷 필요]` · `[다이어그램 필요]` 빈칸 목록.
- **공고 매핑 표**: 요건별로 어떤 프로젝트 · 어떤 서술이 대응하나. 근거 없는 요건은 빈칸.
- **예상 면접 질문 10개**: 작성된 선택 · 트러블슈팅 서술에서 나올 질문. 답이 막히는 곳을 찾는 용도.

## H. 자체 검증 (출력 직전)

- [ ] 프로젝트 수가 3~5개인가 (제출 제약이 있으면 그 안인가)
- [ ] 케이스마다 문제 / 역할 / 해결 과정 / 결과 / 한계가 있는가 (원자에 없는 칸은 비우거나 질문)
- [ ] 이유가 붙지 않은 도구 · 기술 이름이 없는가
- [ ] 근거 없는 정도 표현("대폭 개선", "크게 향상")이 없는가
- [ ] '우리 팀은' 주어 문장이 0개인가
- [ ] 제출본에 다른 사람의 실명 · 아이디가 0건인가 (익명 표기로)
- [ ] E-2의 페이지가 들어가지 않았는가
- [ ] 모든 외부 링크가 실제로 열리는가
- [ ] 비밀유지 제약이 있으면 회사명 · 브랜드 · 실데이터가 노출되지 않는가
- [ ] 쪽수 · 용량 제한을 넘지 않는가
- [ ] 프로젝트마다 레이아웃 · 항목 위치 · 설명 수준이 통일돼 있는가

## I. 참고

- **직무별 강조 축**: 같은 프로젝트라도 직무에 따라 앞에 둘 면이 다르다(예: 백엔드는 데이터 · 확장성, 프론트엔드는 접근성 · 렌더링, 마케팅은 지표 · 실험). 프로젝트 선별은 `strategy.md`의 배치를 따르고, 이 축은 고른 프로젝트 안에서 무엇을 앞에 둘지 정할 때 쓴다.
- **비밀유지 대응 3가지**: 과정 이미지 중심 / 정보 마스킹 / 브랜드 일반화. 사용자가 고른다.
